      In short

      Most comparisons of search APIs call a search a success when the response has status 200 and ten results in it. By that measure every provider scores 99%. That number has stopped meaning much, for two reasons.

      • Hidden addresses. Google no longer puts the address of a result into the page. It puts a link to itself, google.com/goto?url=…, and limits how many of them can be opened per page. An API can return ten results of which half point back at Google.
      • Poisoned pages. Google sometimes answers a scraper with a normal-looking page whose results are fake: sites that do not rank for the search. Same status, same layout, same number of results. Nozzle's study of 68.7 million result pages found this on more than a quarter of them.

      So every answer goes through three checks, in order. Only an answer that passes all three is a usable answer, and that is the main number on this page.

      1. Same search, same secondFrom a published list, to every provider at once, four times a day. One attempt, no retries.
      2. Did it succeed?A valid response within 60 seconds with at least three results.
      3. Are the URLs resolved?Result links must point at websites, not back at google.com. We count the share of links that do.
      4. Is it poisoned?The sites must be the ones this search usually returns, or the ones another provider got in the same minute.

      What we send

      The searches. Two lists of searches, each search with a country and a language, both published in the repository. A core of forty is sent every day: the same searches every day are what makes one day comparable with the next, and what gives the third check its history. A wider list of 160 rotates: forty of them go out each day, so every one of them comes back exactly every four days. About half of all the searches are commercial (loans, insurance, software, shopping), because that is where poisoning concentrates. The rest are questions, local searches, people and places, how-to and technical searches, in six languages, Japanese among them. Which searches go on which day, and in what order, follows from the date alone, so anyone can recompute what was sent. Both lists are public, so a provider that wanted to treat exactly these 200 searches differently could; what a wide rotating list does is make that a lot of work instead of a little.

      The timing. Four runs a day, at hours that shift from day to day so that every hour gets its turn. Within a run a search is sent every 15 seconds on a fixed timetable, whether or not the previous one has come back. A slow provider cannot make us wait and so hide its slow answers.

      Same second, same question. Each search goes to every provider at the same moment, with the same words, country, language and device. Google's results change by the minute; sending at the same moment is what makes the answers comparable.

      One attempt. We never retry. If a provider retries inside its own call, that time is part of its answer.

      The product. Each provider's cheapest real-time Google search endpoint, with default settings and its cache switched off. The exact endpoint and every parameter we send are listed per provider in the repository.

      Step 1 · Did it succeed?

      A search succeeded when all of this is true:

      1. The complete response arrived within 60 seconds.
      2. The status is HTTP 2xx. We do not follow redirects.
      3. The body is valid JSON and does not report an error in the provider's own words.
      4. There are at least three organic results, each with a title and a full http(s) address.
      5. If the provider says which search and country it actually used, they are the ones we asked for.

      The first check that fails names the failure: timeout, network error, HTTP 429, another 4xx, 5xx, invalid JSON, provider error, empty results, malformed results, wrong parameters. Each search gets exactly one outcome.

      What does not count against a provider. Problems on our side: an expired key, used-up credit, a kind of search the provider does not offer. Such a search is set aside for that provider, shown as a separate count and left out of every percentage.

      Response time is measured from sending the request to the last byte of the body, for successful searches.

      Step 2 · Are the URLs resolved?

      A result is only useful if you know where it leads. Since Google hides the address behind its own redirect, a provider has to resolve it: ask Google where each link goes, within Google's limit per page. Some resolve all ten, some only the top few, and it changes from week to week.

      Example · the address field of a result
      resolvedhttps://www.nike.com/running
      not resolvedhttps://www.google.com/goto?url=CAESOmh0dHBzOi8v…
      not resolvedhttps://www.google.com/url?q=…&sa=U
      not resolved/goto?url=CAES…
      not resolved(empty)

      An address counts as not resolved when it points at a Google search host (/goto, /url, /aclk, /search, a block page), is relative, or is empty.

      The number is the share of result links that are resolved, over all successful pages. A page with nine addresses out of ten gives nine tenths of what it should, and the number says exactly that.

      For the next step a page still has to be whole: only a page where every link is resolved is compared with the others, because for anyone who tracks rankings one missing address is one missing site. How many pages were whole is counted next to the number and shown with it.

      Step 3 · Is the page poisoned?

      A poisoned page cannot be told from a real one by looking at it, and nobody can ask Google for the "true" results to compare with. What can be used is how fake pages behave: they are random. Two fake pages fetched separately do not match each other, while real pages for the same search do. And real rankings move slowly, a site or so a day; a fake page changes nearly everything at once.

      We compare which sites are in the first ten (their domains), not the exact addresses and not the order. Three signals:

      1. The sites this search usually returns

      For every search on the fixed list we keep the pages of the last 14 days that were confirmed clean. A site that is on at least 60% of them is one of the search's usual sites. The check says nothing until a search has at least five such pages from three different days: one day is not a history. A new page that carries 60% or more of the usual sites passes. Below 40% it fails. Between the two it is doubtful and is counted neither way. The rule is not ours: it was published by two rank trackers, DemandSphere and Nozzle.

      2. What the other providers got in the same minute

      Two pages agree when at least half of the sites of the shorter one are on the other. The largest group of pages that all agree with each other, from at least two different providers, is taken as real. A page outside the group that still agrees with some page of it is doubtful and is counted neither way; a page that agrees with none fails. This is not a majority vote: if two providers out of five return matching pages and the other three return three different ones, the two are right. Fakes do not match each other; real pages do.

      3. Asking again

      A first page that matches nobody is requested once more from the same provider, after the last measured search of the run, so that the repeat cannot slow a measured search down. If the repeat brings the usual sites or matches the group, the first page was a one-off fake. If it brings the same odd page, the problem is lasting: a poisoned session, the wrong country, a stale cache. A third, different page is the mark of random substitution. The repeat is used only to classify; it is never counted as a success and its time is not measured.

      Example · personal loans online · United States
      Usual sitessofi.com · lendingtree.com · nerdwallet.com · bankrate.com · discover.com · upstart.com · wellsfargo.com · lendingclub.com
      cleanPage A has 7 of the 8 usual sites, and matches what two other providers returned.
      poisonedPage B has 1 of the 8, matches no other provider, and the repeat returned the usual sites.
      not verifiedPage C has 4 of the 8 (50%) and no other provider's page to compare with.

      The verdict

      • Clean: the page passes the history check, or belongs to the agreeing group.
      • Poisoned: it fails every signal that was available.
      • Could not verify: there was neither history nor an agreeing group, or the page was doubtful. It is shown separately and is never counted as clean.

      When a page fails the history check but agrees with the other providers, every provider moved at once: that is a Google update, not poisoning, and the history is refreshed. A page for the wrong country counts as poisoned too: for the buyer it is the same thing, someone else's results presented as theirs.

      Only resolved addresses are compared, because an unresolved one would look like the site "google.com". The detector uses published rules only and never takes ScrapeBeaver's own results as the reference; otherwise we would be judging ourselves.

      How each number is calculated

      Every search ends in exactly one outcome, so the shares below add up.

      Example · 1,000 searches sent to one provider
      1,000 sent980 succeeded → success rate 98.0%
      980 succeeded9,310 of their 9,500 result links resolved → resolved URLs 98.0% · 950 pages had every link resolved
      950 whole pages920 verified: 900 clean, 20 poisoned → poisoned results 2.2% · 30 could not be verified
      Result900 usable answers out of 1,000 sent → usable answers 90.0%

      AI Overview is counted apart from the three checks: an answer without it is still a usable answer. We look at what comes back from the same ordinary search, with no option asked for and at the same price, and count the overview's own text: its sources, addresses and tokens are left out, and less than 200 characters is a first line, not the overview. Google shows an overview for some searches only, so a search is taken to have had one when at least two providers returned its text, and each provider is counted on those searches. Several providers return the overview through a second request or another product, often at a price; that path is not measured, and the pricing page says what it costs where the provider states it.

      How prices are compared

      Providers sell searches in different currencies of their own: requests, credits with multipliers, dollar balances, prepaid packs. To compare them we ask one question of each: what would this many searches a month really cost, by its published prices and its own terms, and what does that come to per 1,000?

      • A plan larger than needed is paid in full. If 10,000 searches need a $40 plan, they cost $4.00 per 1,000 even though the plan could hold more.
      • What happens when a plan runs out differs by provider, and we follow each one's own terms. Where a provider bills further searches on top of a plan, we take the smaller plan plus that overage when it comes to less than the next plan. Where it buys the plan again, we count the plan as many times as it takes. Where it simply refuses requests, the only way is the next plan up, paid in full.
      • Every price in the table shows the month's bill behind it. Point at the bill, or tap it, to see the plan, what is paid on top of it and the whole calculation.
      • Nothing is worked out by hand. Each provider's plans, units per search and terms at the limit are written down in one file with a link for every figure, and one set of formulas turns any such file into prices. A new provider, or a new kind of pricing, goes through the same formulas.
      • One search is the cheapest real-time Google search: desktop, first page, ten results. What it costs in the provider's units is taken from its documentation, with the link.
      • Annual prepayment, negotiated discounts and paid add-ons are left out.
      • A prepaid pack is spread over the months it lasts at that volume, up to its expiry and never more than a year.
      • Above the largest published plan the price is not published. We do not extend the line.

      One volume says little: a provider that is the dearest at 10,000 searches can be the cheapest at a million. That is why prices are shown at every volume, and as a curve, on the pricing page.

      Price per 1,000 usable answers is what the searches were charged, at the list price, divided by the answers that passed all three checks. Poisoned pages and pages with unresolved addresses look like successes, so they are charged like successes.

      Said and measured. What a provider says it charges for failed searches is shown next to what our account balance actually showed.

      How sure the numbers are

      • Every percentage has a margin. It comes from a sample of searches: about one point either way over 30 days, about five over a single day. Point at a number in the table to see its range.
      • Searches are not independent. Poisoning comes in streaks and a bad hour affects everything sent in it. So the ranges are computed by resampling whole runs and whole searches, not single requests, which makes them wider and more honest.
      • Providers are compared search by search. Everyone got the same search in the same second, so we look at the difference on each one. This mark shows the best result in a column only when the gap to the next provider is too large to be luck. When two providers are that close, nobody gets it.
      • Slow-answer figures need enough answers. A median is shown from 20 successful searches, a 95th percentile from 50. Below that the page says so instead of showing a number.
      • The detector is checked too. A person compares a random sample of pages with an ordinary browser without seeing which provider they came from. How often the detector was wrong is published next to its results.

      Fairness rules

      • This benchmark is run by ScrapeBeaver, which is one of the providers in it. It is a reproducible comparison, not an independent one.
      • Our own key is an ordinary key on an ordinary plan, like the ones we buy from the others. Every provider's plan is named.
      • The code, the list of searches and the record of every single request are public. Any number here can be recomputed.
      • The figures and the records may be reused under CC BY 4.0: quote them with a link to this page. The code is under the MIT licence.
      • The repository stores the sites and a fingerprint of each address, not the providers' full responses.
      • A provider can send a correction to its settings or its price data as a pull request.
      • Past results are corrected only by a public commit that says what changed and why.
      • ScrapeBeaver's bad days are published the same way as anyone else's.

      What this does not show

      • Google web search only, in each provider's cheapest real-time mode. Other engines, maps, shopping and queued modes are not measured.
      • Requests are sent from one place, in the United States. Speed from elsewhere can differ.
      • Uptime is not measured.
      • Slices such as one country or mobile only rest on fewer searches, so their margins are wider and no best result is marked there.
